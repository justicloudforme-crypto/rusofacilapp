# Долг 68: `Story.topic` — замер и два варианта на выбор владельца (08.09.2026)

**Это ЗАМЕР и ПРЕДЛОЖЕНИЕ. Данных не тронуто ни строкой: против боевой базы
выполнялись только `PRAGMA table_info`, `SELECT` и `COUNT(*)`. Ни одной
миграции не запущено. Ничего из части «Два варианта» не сделано — это
решение владельца.**

## 1. Что лежит на проде

| вопрос | ответ, замерен 08.09.2026 |
|---|---:|
| строк `Story` | **325** |
| из них `topic IS NULL` | **325** |
| из них `topic = ''` | 0 |
| различных значений `topic` | **1** (`null`) |

DDL прочитан из `sqlite_master`, а не выведен: `… , "topic" TEXT, …` —
колонка **nullable, без `DEFAULT`**. `PRAGMA table_info('Story')` даёт по ней
`notnull=0, dflt_value=null`.

В `prisma/schema.prisma:302` та же колонка объявлена

```prisma
topic         String   @default("other")
```

то есть **NOT NULL со значением по умолчанию**. Расхождение поимённо:

| сторона | тип | nullability | дефолт |
|---|---|---|---|
| `schema.prisma` | `String` | **NOT NULL** | `'other'` |
| боевая база | `TEXT` | **nullable** | **нет** |

Сбоя тут нет. Колонку добавил `prisma/ensure-schema-sync.ts` голым
`ALTER TABLE "Story" ADD COLUMN "topic" TEXT` — без `NOT NULL` и без
`DEFAULT`, потому что SQLite отказывается добавлять NOT NULL-колонку без
дефолта в непустую таблицу. Это его задокументированное свойство (PROGRESS
7.8), и оно будет повторяться с каждым новым полем такой формы.

## 2. Откуда фильтр каталога берёт список тем

**Не из данных.** Список зашит в код:

* `src/lib/stories.ts` — `storyTopics`, восемь ключей
  (`daily_life`, `family`, `work_study`, `childhood`, `mystery`,
  `nature_travel`, `wisdom_morals`, `other`);
* `src/components/stories/StoriesCatalog.tsx:150` — чипы строятся как
  `storyTopics.map(...)`, подписи берутся из словарей
  (`src/dictionaries/{es,ru}.json`, ключ `stories.topics`);
* `src/lib/stories-catalog.ts:86` — при чтении строки `topic` приводится:
  `isStoryTopic(row.topic) ? row.topic : "other"`. Именно это приведение
  превращает 325 `null` в 325 «Otros / Разное» и не даёт странице упасть.

То есть фильтр показывает восемь корзин независимо от того, что лежит в
базе, а данные лежат ровно в одной из них.

## 3. Что видит аноним в отрендеренном DOM (живой прод, обе локали)

Замер 08.09.2026, Chromium, анонимный контекст, `/es/stories` и
`/ru/stories`, по восемь нажатий на локаль — **16 измерений из 16**.

| | `/es/stories` | `/ru/stories` |
|---|---:|---:|
| чипов темы в DOM | **8 из 8** | **8 из 8** |
| метка «Tema» / «Тема» в СЕРВЕРНОМ HTML | есть | есть |
| карточек при «Todos» / «Все» | 24 (страница), ссылок на рассказы в DOM 349 | 24, ссылок 349 |
| карточек при любой из **семи** настоящих тем | **0** | **0** |
| карточек при «Otros» / «Разное» | 24, ссылок 349 | 24, ссылок 349 |

349 = 24 видимых карточки + 325 ссылок серверного индекса, который
отрисован для краулера и от фильтра не зависит; поэтому «0 карточек» — это
именно пустая выдача фильтра, а не пустая страница.

Читатель, нажавший любую тему кроме «Otros», получает пустой список. Семь
чипов из восьми на обеих локалях не работают, и это видно анонимно, без
подписки и без JS-ошибок.

## 4. Почему долг 6 этого не увидел

Долг 6 (закрыт 29.08.2026) сверял `PRAGMA table_info` по 22 моделям и
задавал ровно один вопрос — **есть ли колонка**. Колонка есть. Ни типа, ни
`notnull`, ни `dflt_value` он не читал, и вопроса «сколько строк в
NOT NULL-колонке пусты» не задавал никто.

Закрыто в этом заходе: `npm run check:schema-drift`
(`scripts/check-schema-drift.ts`) сверяет по каждому скалярному полю каждой
модели наличие, `notnull`, `dflt_value` и семейство типа, а для колонки,
которая в схеме NOT NULL, а в базе nullable, печатает **число пустых строк**.

**Позитивный контроль обязателен и прогнан** (`check:schema-drift:plant`,
три подсадки в ТЕКСТ схемы + отрицательная половина «та же находка не
появляется без подсадки»):

| подсадка | локальная база | боевая база |
|---|---|---|
| nullable-колонка объявлена NOT NULL (форма долга 68) | поймано | поймано |
| дефолт в схеме не тот, что в базе | поймано | поймано |
| колонки, объявленной в схеме, в базе нет | поймано | поймано |
| **итого** | **3 из 3** | **3 из 3** |

Настоящий прогон против прода нашёл **3 расхождения**, и одно из них никто
не заводил долгом:

```
User.streakFreezesLeft: дефолт — в схеме 2, в базе нет дефолта
Story.topic: nullability — в схеме NOT NULL, в базе nullable — пустых строк 325 из 325
Story.topic: дефолт — в схеме 'other', в базе нет дефолта
```

`User.streakFreezesLeft` объявлен `Int? @default(2)`: nullable с обеих
сторон, расходится только дефолт, и цена этого мала — Prisma подставляет
значение сама, а строк в таблице на проде 7, из них с `NULL` одна. Записано
как находка, а не как долг.

Против локальной базы та же проверка зелёная: `dev.db` создан
`prisma db push`, поэтому там `topic` NOT NULL — и это ровно то, почему
расхождение нельзя было увидеть, не спросив ПРОД.

## 5. Какое состояние я считаю верным

**Верным считаю не то, что записано в схеме сегодня.** Схема обещает
`String` — необязуемое к проверке обещание: `ensure-schema-sync` физически
не может выполнить его на непустой таблице, а второго механизма миграций у
проекта нет вовсе. Тип, который Prisma отдаёт коду (`string`), уже сегодня
не соответствует тому, что приходит (`null`), — и приведение в
`stories-catalog.ts:86` существует именно потому, что кто-то это
подозревал.

Поэтому верное состояние такое:

1. **`topic String?` в схеме** — правда вместо обещания. Единственное место
   чтения уже приводит `null` к `"other"`, так что ни одного нового
   `if` не появится.
2. **Данные заполнены**, чтобы фильтр перестал показывать семь пустых
   корзин. Это отдельный вопрос от типа — см. вариант (б).
3. **Расхождение сторожится** — `check:schema-drift`, уже написан.

Обратный путь — привести БАЗУ к схеме — тоже возможен, и вот что он значит.

### Что сделала бы миграция (НЕ запускалась)

SQLite не умеет `ALTER COLUMN`. Привести колонку к `NOT NULL DEFAULT
'other'` можно только перестройкой таблицы:

```sql
PRAGMA foreign_keys=off;
BEGIN;
CREATE TABLE "Story_new" ( … "topic" TEXT NOT NULL DEFAULT 'other', … );
INSERT INTO "Story_new" SELECT …, COALESCE("topic",'other'), … FROM "Story";
DROP TABLE "Story";
ALTER TABLE "Story_new" RENAME TO "Story";
-- заново: все индексы и внешние ключи, ссылающиеся на Story
COMMIT;
PRAGMA foreign_keys=on;
```

Тронуло бы: **325 строк** `Story` (перезапись всей таблицы), плюс проверка
ссылающихся строк — `StoryReadingProgress` **28**, и логические ссылки без
внешнего ключа: `AudioAsset(contentType='story')` и `GrammarCheckResult`.
Это самая дорогая и самая опасная из трёх операций на этой странице, и
ради значения по умолчанию, которое код и так подставляет, я её не
рекомендую.

Дешёвый вариант той же идеи — **`UPDATE Story SET topic='other' WHERE topic
IS NULL`**: тронул бы **325 строк из 325**, оставил бы колонку nullable и
не изменил бы на странице **ничего** (все 325 и так показываются как
«Otros»). Смысла в нём нет никакого — он записывает в базу то, что уже
делает код.

## 6. Два варианта на выбор владельца

### (а) Скрыть фильтр, который ничего не фильтрует

**Что делается.** Ряд чипов «Tema / Тема» не рендерится, пока в каталоге
меньше двух различных тем. Правило по ДАННЫМ, а не по флагу: как только
темы появятся, фильтр вернётся сам.

**Числа.** Убирает **7 пустых корзин из 8** на **двух** локалях — 14
нажатий, каждое из которых сегодня даёт пустой список. Строк данных
тронуто **0**, замороженных страниц тронуто **0** (страница `/{lang}/stories`
в список 330 не входит; в нём 130 адресов самих рассказов и 200 медиа).
Правка — один компонент, `StoriesCatalog.tsx`, плюс сторож «фильтр с одной
корзиной не показывается» и подсадка к нему.

**Чего это НЕ делает.** Каталог из 325 рассказов остаётся без единого
среза, кроме уровня и «только классика».

### (б) Проставить темы

**Что делается.** `npm run db:tag-story-topics` — классификация по тем же
восьми существующим категориям (одна модель, одна тема на рассказ,
`other` — явный ответ модели, а не запасной путь).

**Числа — не оценка, а готовая разметка.** В репозитории лежит
`prisma/.tag-story-topics-progress.json` — контрольная точка прогона от
**26.08.2026**, в ней классифицированы **все 325** рассказов:

| тема | рассказов |
|---|---:|
| `daily_life` | **107** |
| `work_study` | **87** |
| `wisdom_morals` | **40** |
| `family` | **39** |
| `childhood` | **25** |
| `nature_travel` | **13** |
| `mystery` | **7** |
| `other` | **7** |
| **всего** | **325** |

То есть после разметки непустыми станут **8 корзин из 8**, а самая крупная
соберёт 107 рассказов (33%) — фильтр начнёт делить каталог, а не
переименовывать его.

**Сколько из них замороженные: 65 из 325.** В списке заморозки 130 адресов
рассказов (65 страниц × 2 локали) плюс 200 адресов медиа — всего 330.
Запись `topic` не меняет ни одного из пяти полей, которые сторожит
`check:frozen` (`status`, `title`, `description`, `canonical`, `h1`), но
правило владельца сформулировано как «не трогать **ни данными, ни кодом**»,
поэтому это решение владельца, а не вывод скрипта. Безопасный порядок, если
вариант выбран: разметить **260 незамороженных**, а 65 замороженных оставить
на после 25.09.2026 — тогда тронутых замороженных строк **0**, а корзины
наполняются уже сегодня.

**Чего я НЕ смог измерить.** Разбивку «сколько замороженных в каждой теме».
Контрольная точка ключуется по `id` рассказа, а пересев 08.09.2026 заменил
локальные `id` продовыми — совпадает **10 ключей из 325**, и связать
разметку с адресами заморозки нечем. Восстанавливается повторной
классификацией 65 замороженных рассказов (65 вызовов модели); в этом заходе
не делалась, потому что заход — замер, а не трата ключа.

**Цена варианта (б):** один прогон скрипта против боевой базы (325 или 260
`UPDATE`), деньги за 325 вызовов gpt-4o-mini — или ноль вызовов, если
принять разметку от 26.08 как есть, сопоставив её по `title`, а не по `id`
(тем же приёмом, каким пересев сводил рассказы: дублей заголовков 0 с обеих
сторон).
