**Четыре вопроса, на которые замер ответил.**

1. **Страница вбок не едет.** `document.scrollWidth` равен вьюпорту во
   всех 24 измерениях. Прокручивается карточка, а не документ — то есть
   дефект 7.60, из-за которого правило и писалось, здесь не повторён.
2. **Пальцем доска возится.** Настоящий свайп (CDP
   `Input.synthesizeScrollGesture`, `gestureSourceType: touch`) сдвинул
   `scrollLeft` 0 → 152 и на B1/304, и на B1/91. Контроль рядом: у
   филворда `touch-action: none` и прокручивать нечего.
3. **Палец попадает по клетке.** Тап по видимой клетке даёт ей фокус в
   обоих движках. Первый замер сказал обратное — и был **артефактом**:
   тапали по клетке, увезённой за правый край карточки, координата
   оказывалась вне вьюпорта, и события не было ни одного
   (`elementFromPoint` вернул `undefined`). Контроль поймал это сам:
   тап по обычному полю на `/es/login` и по клетке филворда работал.
4. **Клавиатура клетку не прячет.** Смоделирована сжатием вьюпорта до
   444px (780 − 336, клавиатура iPhone 13 с панелью подсказок). На
   B2/168 — самом высоком пазле банка (43 строки, доска 1030px) — первая,
   средняя и последняя клетки после фокуса видимы все три. Поле ввода не
   `position: fixed`, поэтому браузер доскролливает его сам; автопротяжка
   через правый край доски тоже везёт доску за фокусом (`scrollLeft`
   0 → 152 на слове «полуостров», столбцы 7…16).

**Порог филвордов на кроссвордах недостижим, и вот число.** Чтобы 46
столбцов поместились в 272px, клетка должна быть **3,9px**; даже медиана
в 23 столбца требует **9,9px** — против 14,9px, принятых у филвордов при
320px как самое узкое ДОСТИЖИМОЕ значение. То есть «вся доска на экране»
для кроссвордов не порог, а другой продукт.

**Крупная переделка не начата — решение за владельцем.** Три честных
пути, если 22px и панорамирование покажутся недостаточными:

1. **Зум/панорамирование как явная механика** — доска в
   `overflow: auto` с двойным тапом на «вписать целиком»; дёшево, ничего
   в данных не меняет, но мелкий текст остаётся мелким.
2. **Разбиение широких пазлов при генерации** — потолок ширины
   (например 14 столбцов, помещается при 390px) и перегенерация: трогает
   1071 строку банка и весь их подбор слов.
3. **Вертикальная раскладка на телефоне** — показывать по одному слову с
   его пересечениями, как в мобильных кроссвордах: самая большая работа,
   зато 22px перестают быть потолком.

**Что вместо правки.** Пинуется измеренное: `e2e/word-games.spec.ts`
получил тест «доска шире телефона намеренно», который открывает B1/91
(46×11, самая широкая строка банка, добавлена в фикстуру) и требует все
четыре свойства выше. Позитивный контроль — три подсадки, каждая со
сборкой и прогоном: `touch-none` на сетке («сетке запрещено
панорамирование»), снятый `max-w-full` со скроллера («страница поехала
вбок»), снятый пол 22px (доска перестаёт быть шире карточки). Снятие

широкий кроссворд из фикстуры пропал, — иначе тест стал бы зелёным
вакуумно. Пол `check:e2e-coverage` 79 → **81**.

было — `focusCell` был голым `.focus()`, и утверждение о видимости
опиралось на встроенную доводку движка.** Доказано замером по шагам на

#### Бесплатных кроссвордов 40, а не 50 — правило, а не дыра

Ожидание «первые 10 рунгов пяти уровней = 50» не сходится с кодом.
`src/lib/word-games/free-tier.ts:29-34`:

```ts
export function isFreeWordGamePuzzle(puzzle: { type: string; level: string; sequence: number }): boolean {
  return (
    (puzzle.type === "WORD_SEARCH" || puzzle.type === "CROSSWORD") &&
    puzzle.level !== "C1" &&
    puzzle.sequence <= WORD_GAME_FREE_RUNGS_PER_LEVEL

}
```

#### Ошибка A: `.catch()` стоял и работал — а событие уходило из другого вызова

Событие: `SecurityError: Script https://rusofacilapp.com/sw.js load
failed`, DOMException code 18, Safari 26.5 на Mac, `handled = no`,
`mechanism auto.browser.global_handlers.onunhandledrejection`, url
`/es/word-games/WORD_SEARCH/B2/10`.

Напрашивавшийся диагноз — «у промиса регистрации нет обработчика» —
**неверен**: обработчик в `SerwistRegister.tsx` стоял с 31.08 и в замере
отрабатывает (его `console.warn` виден в той же консоли, где событие).
Починка 31.08 (не звать `register()` для 11 краулеров + проверка наличия
`serviceWorker` в `navigator`) этот случай тоже не покрывает — объект в
приватном окне Safari существует.

**Настоящая причина найдена в собранном бандле, а не рассуждением.**
`@serwist/next` подшивает свой модуль `sw-entry` в начало входных чанков
`main` и `main-app` (см. `node_modules/@serwist/next/dist/index.mjs`,
`config.entry`), и опция плагина `register` по умолчанию **`true`**. В
`next.config.ts` она не задавалась, а `register={false}` у
`<SerwistProvider>` в `[lang]/layout.tsx` гасит **другой** вызов —
внутри React-провайдера — и на вебпак-плагин не влияет вовсе. В боевом
бандле от 02.09.2026 лежало буквально это:

```js
window.serwist = new i(window.location.origin + "/sw.js", { scope: "/" }),
  …, location.pathname.startsWith(t) && window.serwist.register(),
```

— без `.catch()`, на этапе выполнения входного чанка, до гидратации.

**Замер (WebKit, тот же движок, что у Safari).** `navigator.serviceWorker`
подменяется на форму приватного окна: объект есть, `register()` отвергает
промис с `SecurityError`. На сборке ДО починки:

| | до | после |
|---|---|---|
| необработанных отказов в окне | **1** (`SecurityError: Script …/sw.js load failed`) | **0** |
| `console.warn` из `SerwistRegister` | есть | есть |

#### Ошибка B: «handled = yes» — это наши собственные границы ошибок

Событие: `TypeError: Load failed`, Mobile Safari 26.6.1, iPhone,
`handled = yes`, `mechanism generic`, transaction
`/:lang/word-games/:type/:level/:sequence`, url
`https://rusofacilapp.com/ru/word-games`.

**Место найдено:** шесть `error.tsx` (`word-games`, `stories`, `profile`,
`vocabulary`, `media`, `[lang]`) и `global-error.tsx` — каждый делал
`Sentry.captureException(error)` без разбора. Замером подтверждено, что
именно этот вызов даёт ровно ту подпись: в прогоне с перехватом конверта
`captureException` дал `mechanism: {type: "generic", handled: true}` и
`transaction: /:lang/word-games/:type/:level/:sequence` — совпадает с
боевым событием посимвольно.

**Что грузил упавший запрос — прямой ответ: это ЧТЕНИЕ, а не сохранение.**
Проверены все записи этой поверхности, поимённо:

| запрос | что это | было |
|---|---|---|
| `POST /api/word-games/complete` | результат пазла | `fetch(...).catch(() => {})` |
| `POST /api/word-games/check` | проверка клетки | `await fetch(...).catch(() => null)` |
| `POST /api/word-games/hint` | подсказка | `.then().catch(() => {})` |
| `POST /api/flashcard-progress` | прогресс карточек | `fetch(...).catch(() => {})` |
| отметка дня (`StudyDay`) | — | пишется **на сервере** в `after()`, клиентского запроса нет вовсе |

Ни один из них ничего в Sentry не отправляет — значит, событие не от них.
Воспроизведение в WebKit при обрыве сети даёт в консоли ровно ту строку
(`Failed to fetch RSC payload for …/ru/word-games. Falling back to browser
navigation. TypeError: Load failed`) и оставляет url на `/ru/word-games`
при активной транзакции страницы пазла — то есть упавший запрос был
**загрузкой страницы (RSC-полезной нагрузки), а не записью**. Сам
маршрутизатор Next в этом случае в Sentry ничего не шлёт (замерено:
конвертов ноль), а вот граница ошибок, если до неё доходит, шлёт всё.

**Что изменено.**

- `src/lib/report-boundary-error.ts` (+ тест) — глушится **только
  отменённое**: `AbortError` всегда, а сетевой отказ — лишь когда
  документ уже уходит (`pagehide`) или спрятан
  (`visibilityState === "hidden"`). Решение принимается по **состоянию
  страницы**, а не по тексту: WebKit пишет «Load failed» и при настоящем
  отказе сети, и при отмене. Настоящий отказ на живой странице остаётся
  видимым — это прямо закреплено тестом.
- `src/lib/reliable-post.ts` (+ тест) и два места вызова
  (`WordGamePlayer`, `flashcard-progress`) — `keepalive: true` (запрос
  доживает после выгрузки документа), повтор с растущей паузой на сети,
  5xx и 429, **без** повтора на 4xx, маячок `sendBeacon` последним
  рубежом, и честный возврат «потеряно» вместо молчания.

**Оговорка, которую надо назвать вслух.** Отправка результата пазла
чинится не потому, что она была источником события B — она им не была, —
а потому, что при разборе выяснилось: это единственное свидетельство
решённого пазла, и оно уезжало `fetch(...).catch(() => {})` ровно в тот
момент, когда ученик уходит со страницы. Это и есть «потерянная запись»
из постановки задачи, просто не та, что видна в Sentry.

#### Что найдено вместо этого: ключ дня стамповался зоной, известной на момент ЗАПИСИ

`StudyDay.dateKey` — единственный из шести источников, который **не**
пересчитывался в зоне читателя: он писался готовой строкой в момент
отметки, а остальные пять хранят мгновение и переводятся в день при каждом
чтении. Зона на момент записи берётся так
(`src/lib/timezone-server.ts:20`): колонка `User.timezone` → cookie
`rusofacil-tz` → UTC. Cookie пишет клиентский эффект
(`src/components/TimeZoneSync.tsx:19`), то есть **на самом первом ответе
нового браузера её ещё нет** — а это ровно тот ответ, который отмечает
первый день ученика. В Мехико в 19:00 UTC-ключ — это **завтра**.

| | |
|---|---|
| строк `StudyDay` на проде | **5** |
| из них со штампом, не совпадающим с локальным днём | **0** — правка ничего не переписывает и не могла бы |
| цена дефекта на моделируемых данных | три вечера подряд превращаются в 2 дня вместо 3 (`src/lib/study-day-key.test.ts`) |

Починено с двух сторон:

1. **Источник.** `getRequestTimeZone` получил третий источник —
   `x-vercel-ip-timezone`, заголовок самого запроса, который есть до того,
   как выполнится любой скрипт. Третий, а не первый: IP говорит, откуда
   соединение, а не где человек.
2. **Чтение.** `src/lib/study-day-key.ts` (новый) выводит день из
   `markedAt` в зоне читателя — как и остальные пять источников. Побочно
   это чинит и разъезд «пять источников на новом календаре, шестой на
   старом» у сменившего зону. Оговорка названа прямо: у переехавшего
   прошлые дни сдвигаются на разницу — но так уже ведут себя пять из шести.
3. **Столкновение.** Строка, занявшая чужой ключ, раньше молча блокировала
   отметку следующего дня (`findUnique` находил её и выходил). Теперь она
   переносится на свой день, а сегодня отмечается; если её день уже
   отмечен другой строкой — удаляется как дубль. Единственное удаление во
   всём пути отметки, и оно возможно только когда день остаётся на
   календаре.

`markedAt` теперь пишется явно (`markStudyDay`), а не берётся из
`DEFAULT now()`: на проде это то же самое, но фикстура, подающая мгновение,
раньше получала строку с чужим временем.

#### Причина закрыта в коде — и оказалась опаснее, чем формулировалась

`prisma/generate-word-games.ts` читал карточки без `orderBy`, то есть в
порядке rowid — артефакте того, в каком порядке строки легли в конкретный
файл. `candidateWords()` дедуплицирует «первый выигрывает» по этому
порядку, а `buildWordSearch`/`buildCrossword` тасуют пул сеяным ГПСЧ;
сеяное тасование — это перестановка ВХОДНОГО массива, поэтому тот же seed
на иначе упорядоченном пуле выбирает другие слова. Добавлен
`orderBy: { id: "asc" }` в оба чтения (уровень и `lowerCards`). `id`
карточки — человекочитаемый слаг (`v6-fridge`), одинаковый в обеих базах:
5678 из 5678 локальных id есть и на проде.

**И тут посылка задачи не подтвердилась.** «Генератор пишет только
недостающие» было неверно: `upsertPuzzle` сравнивал содержимое и молча
ОБНОВЛЯЛ любую разошедшуюся строку. Замер:

| прогон `--dry-run` по неизменной `dev.db` | результат |
|---|---|
| до правки | `0 would be written, 3000 already up to date` |
| после `orderBy`, как было | **`2979 would be written`** — то есть 99,3% банка, включая строки с прогрессом игроков |

2979 — то же число, что в эксперименте 7.82 с перестановкой карточек.
Поэтому свойство «пишет только недостающие» пришлось не констатировать, а
СДЕЛАТЬ: перезапись существующей строки ушла под флаг `--rewrite`,
которого по умолчанию нет. Строки, которые прогон построил бы иначе, не
пропадают молча — они считаются и печатаются списком.

| прогон | результат |
|---|---|
| `--dry-run` (по умолчанию) | **`0 would be written`**, отдельной строкой «2979 existing puzzle(s) left as they are» |
| `--dry-run --rewrite` (позитивный контроль) | `2979 would be written` — сторож настоящий, а не сломанный скрипт |

#### Диагноз расхождения банков: порядок строк `FlashcardCard`

7.81 оставил вопрос открытым («полного решения, почему id вообще
разошлись, не искали»). Ответ найден **контролируемым экспериментом**, а
не рассуждением, и воспроизводится одной командой.

Генератор объявляет себя детерминированным: «seeded from
`${type}-${level}-${sequence}`, re-running reproduces byte-identical
puzzles». Это верно с одной невысказанной оговоркой — карточки читаются
запросом `db.flashcardCard.findMany({ where: { level } })` **без
`orderBy`**, а дальше `candidateWords()` дедуплицирует «первый выигрывает»
по порядку выдачи, и `buildWordSearch`/`buildCrossword` тасуют пул
(`shuffle(pool, rng)`). Тасование сеяного ГПСЧ — это перестановка
ВХОДНОГО массива: тот же seed на иначе упорядоченном пуле даёт другую
выборку слов. Порядок выдачи без `orderBy` — это порядок хранения строк
(rowid), и он у двух независимо засеянных баз разный.

Эксперимент (две копии `dev.db`, сам `dev.db` не трогался):

| | копия A | копия B |
|---|---|---|
| что сделано с карточками | ничего | те же 5678 строк, переуложены в случайном порядке (`ORDER BY random()`) |
| прогон `generate-word-games` | `0 puzzle(s) written, 3000 already up to date` | `2979 puzzle(s) written, 21 already up to date` |

То есть при неизменном порядке генератор действительно воспроизводит банк
байт в байт (копия A — 0 записей), а **одна только перестановка строк
карточек переписывает 99,3% банка**.

Сравнение содержимого A против B и — тем же способом — прод против
`dev.db` из 7.81:

| | A против B (эксперимент) | прод против `dev.db` (7.81) |
|---|---|---|
| списков слов совпало, WORD_SEARCH | **34 из 1749 (1,9%)** | **37 из 1728 (2,1%)** |
| списков слов совпало, CROSSWORD | **1 из 1262 (0,08%)** | не измерялось |
| список нашёлся под другим номером | 0 | 0 |
| id строк совпало | 1749 из 1749 | **0** |

Совпадение долей 1,9% и 2,1% — количественный отпечаток одного и того же
механизма: столько пазлов случайно устояли при перевыборке. Разница по id
объясняет остальное: в эксперименте строки обновлялись `upsert` по
`(type, level, sequence)`, поэтому id сохранились; на проде совпавших id
ноль, значит продовые строки были **созданы** своим прогоном, а не
скопированы из `dev.db`. Итог: два независимых прогона одного и того же
детерминированного генератора против двух баз, чей порядок хранения
`FlashcardCard` различается.

**Чего этот диагноз НЕ доказывает и что осталось проверить на проде.**
Во-первых, эксперимент показывает, что кроссворды к порядку строк
чувствительны РОВНО ТАК ЖЕ (1 совпадение из 1262). Утверждение «кроссворды
у прода и `dev.db` совпадают 1:1» в 7.81 не измерялось: там сравнивались
только КОЛИЧЕСТВА (`CROSSWORD 1262 против 1262, по уровням совпадает`),

содержимое кроссвордов на проде и правда совпадает 1:1, диагноз выше
неполон и объяснение надо искать в чём-то, что касается только

#### Манифест считается скриптом, а не переписывается руками

`prisma/build-density-manifest.ts` (`npm run db:build-density-manifest`) —
только чтение. Считает метрику по всем строкам ТОЙ базы, против которой

#### Что делать дальше (решение за владельцем)

Манифест нельзя «поправить пятью числами»: 1691 рунг из 1738 на проде
держит не те слова, по которым он считался, поэтому и сам выбор двадцати
рунгов на проде другой. Два честных пути:

1. **Пересчитать манифест по проду.** Снять снимок с прода
   (`--write-baseline=`), выбрать двадцать худших по нему, выписать
   `parts`/`tailSequences` из продовых данных, проверить сверкой, и
   только потом писать. Заодно решить, что делать с четвёрочным классом
   (`C1/114`, `C1/68`, `B2/141`, `B1/400`), которого в локальном
   манифесте нет.
2. **Сначала закрыть расхождение банков** (давний открытый вопрос про
   `dev.db` ↔ Turso), выбрать эталон и привести вторую копию к нему — и
   уже потом разгружать по одному манифесту.

До любого из них разгрузка на проде остаётся неприменённой, и это
безопасное состояние: филворды на проде решаемы (0 ненайденных слов),
просто двадцать из них плотнее, чем хочется.

### 7.78. Разгрузка десяти филвордов: те же слова, больше сеток (02.09.2026, ПРАВКА ДАННЫХ)

**Читать вместе с 7.77.** Там метрика и сторож; здесь — единственная
правка данных, которую метрика вызвала, и почему она безопасна.

#### Что делает

`npx tsx prisma/redistribute-word-search.ts` (алиас
`npm run db:redistribute-word-search`) берёт десять самых переполненных
рунгов, **их собственные слова**, и раскладывает по нескольким сеткам
16×16. Слова не режутся, не заменяются, не дополняются: множество «до» и
«после» сравнивается поэлементно, и расхождение останавливает прогон.

Первая часть пишется **в ту же строку** (`UPDATE` по id) — URL, id и весь
`WordGameProgress` игроков сохраняются. Остальные части — новые строки в
хвосте нумерации уровня, номера **заранее прописаны** в манифесте
`src/lib/word-games/density-rungs.ts`, а не придуманы в проде: если
разложение потребует больше частей, чем обещает манифест, скрипт
останавливается и просит поправить манифест.

#### Почему это не задевает индексацию

Проверено A/B на одной сборке, до и после правки данных:

| | до | после |
|---|---|---|
| URL в `sitemap.xml` (локально) | 1850 | **1850, множество идентично** |
| C1-URL в sitemap | 0 | **0** |
| `robots.txt` | — | **побайтово тот же файл** |
| вердикт robots для всех 11 новых URL | — | **disallowed по `/*/word-games/`** |
| аноним на новом URL | — | **307 → /pricing** |

Краулимое множество (1908 = 1906 из sitemap + `/es|ru/download`) не
меняется: новые sequence далеко за 10, поэтому ни одного `Allow` под них в
`robots.txt` нет, и в sitemap они не попадают по правилу
`level !== "C1" && sequence <= 10`, которое заход не трогал.

#### Ловушка, которую пришлось закрыть в генераторе

`cleanupStaleSequences()` в `prisma/generate-word-games.ts` удаляет всё,
что старше максимальной последовательности лестницы, — а хвост по
построению именно там. Без правки **первый же полный прогон генератора
стёр бы пазлы, в которых живут перенесённые слова**, и слова исчезли бы с
уровня. Поэтому `maxWordSearchSequence()` теперь прибавляет
`densityTailCount(level)`, а сам генератор пропускает рунги, которые
разгрузка забрала себе (`isDensityOwnedRung`).

**Важная деталь пропуска:** сборка пазла и `recordUsage()` всё равно
выполняются, пропускается только запись. Иначе следующий рунг того же
уровня вытянул бы другой набор слов, и полный прогон молча переписал бы
тысячи строк, которых никто не просил менять, — ровно та ловушка, о
которой предупреждает комментарий про темы в самом генераторе.

#### Как это запускать (владелец, с боевым ключом Turso)

```
TURSO_DATABASE_URL="libsql://…" TURSO_AUTH_TOKEN="…" \
  npx tsx prisma/redistribute-word-search.ts --dry-run
```
показывает по каждому из десяти: сколько слов было, какая была занятость,
на сколько частей делится, какие числа у частей и в какие sequence они
лягут. Ничего не пишет. Затем, увидев вывод:

```
TURSO_DATABASE_URL="…" TURSO_AUTH_TOKEN="…" \
  npx tsx prisma/redistribute-word-search.ts --only=B2/44
```
— по одному рунгу, или без `--only=` для всех десяти. **Флага `--force`
нет.** Повторный запуск идемпотентен: хвостовую строку скрипт согласен
перезаписать только если все её слова принадлежат исходному рунгу, иначе
останавливается.

После прогона по проду снимок 7.77 стоит перечитать заново
(`--write-baseline=`), иначе одиннадцать новых пазлов так и будут
печататься как «появились после снимка».

### 7.79. Дыра в лестнице рунгов — сторож перед записью (02.09.2026, КОД)

**Читать вместе с 7.78.** Там разгрузка; здесь единственное, что в ней
могло молча сломаться, и проверка, которая теперь этого не даст.

#### Что нашли

`WordGamesPicker` рисует ссылки так:

```
Array.from({ length: total }, (_, i) => i + 1)
```

где `total` — это `countAllSequences()`, то есть **число строк** пары
(type, level), а не их номера. Никто нигде не спрашивает, какие
sequence на самом деле существуют.

Пока лестница сплошная 1…N, это одно и то же. Сегодня она сплошная у всех
пяти уровней — проверено по всем 1738 строкам снимка
`docs/word-search-baseline-2026-09-01.json`:

| уровень | строк | номера |
|---|---|---|
| A1 | 196 | 1…196, без дыр |
| A2 | 413 | 1…413, без дыр |
| B1 | 562 | 1…562, без дыр |
| B2 | 327 | 1…327, без дыр |
| C1 | 240 | 1…240, без дыр |

Разгрузка (7.78) — **первое, что дописывает строки руками**, и потому
первое, что способно эту сплошность сломать. Ошибка в одном числе
`tailSequences` даёт лестницу вида «333 строки с номерами 1…332 и 340», и
дальше два тихих дефекта сразу: строка 340 недостижима — ссылки на неё не
существует, — а последняя нарисованная ссылка (333) ведёт на 404. Ничего
не падает, ничего не логируется, в CI не видно.

#### Что сделано

`ladderGaps(existing, added)` в `src/lib/word-games/density-rungs.ts`:
по номерам, которые у уровня уже есть, и номерам, которые манифест
допишет, возвращает список пропущенных. Пусто — лестница остаётся 1…N.

`prisma/redistribute-word-search.ts` вызывает её **до первой записи**, по
каждому уровню, который трогает манифест, и при дыре останавливает прогон
целиком, не записав ничего.

Проверяется **весь манифест**, а не выбранные `--only=` рунги: манифест —
это обещание конечного состояния, и дыра в нём остаётся дырой независимо
от того, какой рунг запускают сегодня. Про `--only=` печатается отдельное
предупреждение — до прогона остальных рунгов лестница будет с дырой, и это
нормально ровно до конца прогона.

Контроль, что сторож не декоративный: подменить `tailSequences: [333]` на
`[340]` и запустить `--dry-run` — прогон обязан покраснеть словами
«остаются дыры 334, 335, 336, 337, 338, 339» и не дойти до первой записи.
Проверено.

#### Что ещё закрыто тестами

`src/lib/word-games/density-rungs.test.ts` — инварианты самого манифеста,
без базы: `parts` совпадает с длиной `tailSequences`; ни один источник и
ни один хвост не попадает в бесплатные рунги 1–10 (сравнение с
`FREE_TRIAL_LIMITS.wordGamePuzzlesPerLevel`, а не с литералом 10); ни один
рунг не назван дважды; хвостовой блок уровня идёт подряд, без дыры внутри
себя; `densityTailCount` не расходится с `densityTails`. Плюс четыре теста
на сам `ladderGaps`, включая «пустая лестница — это не дыра в единице».
