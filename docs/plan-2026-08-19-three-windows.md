## Окно 1 — Игровые механики (Sopa de Letras + кроссворд), статическая база

### Принцип
Генератор — отдельный offline-скрипт (`tsx`, по образцу `prisma/generate-story-audio.ts`), запускается вручную командой `npm run generate:word-games`, пишет готовые сетки в БД один раз. Рантайм-код (страница игры, API-роут) НИКОГДА не запускает алгоритм генерации сетки — только `SELECT` уже готовой записи. Если для новых слов нужна новая сетка — перезапустить генератор, а не генерировать на клиенте/сервере по запросу.

### Схема Prisma (добавить в `prisma/schema.prisma`)

```prisma
enum WordGameType {
  WORD_SEARCH   // Sopa de Letras
  CROSSWORD
}

model WordGamePuzzle {
  id          String       @id @default(cuid())
  type        WordGameType
  level       String       // A1 | A2 | B1 | B2 | C1
  // Порядковый номер сложности внутри уровня (1 = самая простая сетка
  // этого уровня, дальше растёт размер сетки/число слов) — даёт
  // прогрессию "от простого к сложному" без отдельной таблицы уроков.
  sequence    Int
  // JSON: { size: number, grid: string[][] } — уже готовая сетка,
  // ничего не пересчитывается на клиенте.
  gridData    String
  // JSON: WordPlacement[] — { word, clue (для кроссворда — translationEs
  // карточки), row, col, direction, number (кроссворд: номер клетки) }
  words       String
  createdAt   DateTime     @default(now())

  @@unique([type, level, sequence])
  @@index([type, level])
}

model WordGameProgress {
  id           String         @id @default(cuid())
  userId       String
  user         User           @relation(fields: [userId], references: [id], onDelete: Cascade)
  puzzleId     String
  puzzle       WordGamePuzzle @relation(fields: [puzzleId], references: [id], onDelete: Cascade)
  completedAt  DateTime       @default(now())
  timeSeconds  Int?

  @@unique([userId, puzzleId])
  @@index([userId])
}
```

Обоснование: `gridData`/`words` как JSON-строка — та же логика, что уже принята в проекте для `FlashcardCard.synonyms`/`GlossaryTerm.examples` (небольшой вложенный набор данных, join-таблица избыточна). `WordGameProgress` — по образцу `LessonProgress`/`GroupMember`, минимальный объём на пользователя.

### Архитектура скрипта-генератора (`prisma/generate-word-games.ts`)

1. Для каждого уровня (A1-C1) выбрать пул слов из `FlashcardCard` (`russian`, `translationEs`), отфильтровав слишком длинные/с пробелами-дефисами для sopa de letras (кроссворд может допускать дефисы отдельной обработкой).
2. **Sopa de Letras**: на уровень — N сеток возрастающей сложности (например, 5 сеток: 8×8/10 слов → 14×14/18 слов). Алгоритм: случайный выбор слов уровня → размещение каждого в случайном из 8 направлений с проверкой конфликтов по занятым клеткам (backtracking, лимит попыток) → заполнение пустых клеток случайными кириллическими буквами с распределением частот, близким к реальному (не равномерным — иначе сетка визуально "не по-русски" читается). Детерминированный `seed` на сетку — чтобы генератор был воспроизводим (одна и та же сетка при перезапуске, пока пул слов не меняется).
3. **Кроссворд**: на уровень — N сеток. Алгоритм: жадное размещение первого (самого длинного) слова в центр → для каждого следующего слова перебор всех возможных пересечений по общим буквам с уже размещёнными словами → ретраи с разным порядком слов при неудаче (сетка не сходится) → при N неудачных попытках — уменьшить целевое число слов в этой сетке и попробовать снова. **Важно**: если для какого-то уровня пул слов даёт систематически мало пересечений (короткие несвязанные по буквам слова), логировать это как отдельную проблему в отчёте генератора, а не тихо выдавать пустые/вырожденные кроссворды.
4. Скрипт идемпотентен: `upsert` по `[type, level, sequence]`, безопасно перезапускать после изменения словаря (хотя словарь сейчас заморожен).
5. Вывести в консоль отчёт: сколько сеток на уровень/тип создано, для каких уровней кроссворд не сошёлся с целевым числом слов (см. п.3) — ручной разбор находок, не автоматический фолбэк на "как получится".

### Список задач (Окно 1)
1. Добавить модели `WordGamePuzzle`/`WordGameProgress` в схему, `prisma migrate`.
2. Написать генератор Sopa de Letras (алгоритм размещения + заполнение), запустить, вручную проглядеть 2-3 сетки на предмет читаемости.
3. Написать генератор кроссворда (алгоритм пересечений + ретраи), запустить, проверить отчёт о несошедшихся уровнях, при необходимости донастроить целевое число слов на сетку.

5. UI Sopa de Letras: сетка, тач/drag-выделение по 8 направлениям, подсветка найденного слова, список слов сбоку с вычёркиванием.
6. UI кроссворд: пронумерованная сетка, список подсказок (по/на основе `translationEs`), ввод по клеткам, проверка.
7. API-роут(ы) на чтение готовой сетки + запись `WordGameProgress` (никакой генерации внутри роута).
8. Прогрессия по уровню (следующая `sequence` открывается после прохождения предыдущей — по аналогии с существующей `LessonProgress`-логикой открытия уроков).
9. Интеграция с уже готовой системой анимаций/звука (`celebration/`) на завершение сетки.
10. Vitest на сам алгоритм генератора (детерминированность, отсутствие конфликтов в сетке, все слова действительно размещены). Playwright на клик/тач-прохождение обеих игр на мобильном вьюпорте.

## Окно 3 — Лингвистический контроль (статический аудит)

### Принцип
Скрипт-валидатор гоняет **весь текущий контент один раз** через LLM с грамматическим промптом, пишет результат (найденные ошибки + статус) в БД/файл. Приложение в рантайме этот скрипт не вызывает никогда — только показывает уже провалидированный контент. Новый контент (если/когда пользователь снова разрешит рост базы) обязан пройти через этот скрипт и получить статус `clean` до заливки в прод — это ворота, а не фоновая проверка.

### Отличие от `prisma/check-typos.ts`
Существующий скрипт — эвристика (опечатки, буквальные повторы слов), НЕ грамматика. Новый скрипт — семантическая проверка через LLM (согласование падежей, вид/спряжение глаголов, порядок слов) поверх уже чистого (по опечаткам) текста. Оба скрипта независимы, оставить оба в `package.json`.

### Схема Prisma

```prisma
enum GrammarCheckStatus {
  PENDING
  CLEAN
  FLAGGED
}

model GrammarCheckResult {
  id          String              @id @default(cuid())
  // Составной "адрес" проверенного поля, а не FK на 4 разные модели —
  // тот же паттерн, что и у generate:*-audio скриптов, которые тоже
  // адресуют произвольную запись по (тип сущности, id, поле).
  entityType  String              // "FlashcardCard" | "Idiom" | "GlossaryTerm" | "Story"
  entityId    String
  fieldName   String              // "russian" | "exampleRu" | "text" | ...
  // Хэш проверенного текста (не сам текст — избегаем дублирования
  // исходных данных) — при повторном запуске скрипт пропускает поля,
  // чей текст не изменился с последней CLEAN-проверки.
  contentHash String
  status      GrammarCheckStatus  @default(PENDING)
  // JSON-encoded массив находок: { errorType, excerpt, explanation,
  // suggestion } — пусто для CLEAN.
  findings    String              @default("[]")
  checkedAt   DateTime            @default(now())

  @@unique([entityType, entityId, fieldName])
  @@index([status])
}
```

### Архитектура скрипта-валидатора (`prisma/check-grammar.ts`)

1. Пройтись по тем же моделям/полям, что уже перечислены в `check-typos.ts` (`FlashcardCard.{russian,exampleRu}`, `Idiom.{phrase,contextExampleRu}`, `GlossaryTerm.{term,russianEquivalent,examples[].ru}`, `Story.{title,text}`).
2. Для каждого поля посчитать `contentHash` (например sha256 текста) и сверить с уже сохранённым `GrammarCheckResult` того же `[entityType, entityId, fieldName]` — если хэш совпал и статус `CLEAN`, пропустить (не тратить вызов LLM повторно на неизменённый текст — критично для стоимости при повторных прогонах).
3. Для новых/изменённых полей — батчить по N штук на один вызов LLM (не по одному полю за вызов — иначе 5678+771+91+325 полей = тысячи отдельных вызовов) с чётким промптом: "проверь ТОЛЬКО грамматику (падежи, вид, спряжение, порядок слов) русского текста ниже, не стиль и не орфографию, верни JSON-массив находок по каждому текст-ID или пустой массив".
4. Записать результат — `CLEAN`/`FLAGGED` + `findings` — по каждому полю в отдельную строку `GrammarCheckResult` через `upsert`.
5. В конце вывести сводный отчёт: сколько полей проверено, сколько `FLAGGED`, с прямыми ссылками на `entityId` для ручного разбора.
6. **Ничего не исправляет автоматически** — только помечает. Исправление находок — отдельный ручной шаг (либо руками, либо отдельным подтверждённым прогоном правок), после которого поле перепроверяется и меняет статус на `CLEAN`.
