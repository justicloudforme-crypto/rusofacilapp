## 0. ЧТО ЭТО ЗА ПРОЕКТ

**RusoFácilapp** — сайт `https://rusofacilapp.com` и Android-приложение
для изучения русского языка **испаноговорящими**. Приложение
«RusoFácil: aprender ruso» (`com.rusofacilapp.app`) — оболочка Capacitor,
которая грузит боевой сайт (`server.url`); **в Google Play с 07.10.2026**
(продакшн, 177 стран + остальной мир). На сайте и в приложении — живые
ученики и платящие подписчики. Владелец — не программист.

**Две локали.** `/es` — основная, под неё написан весь обучающий текст;
`/ru` — русскоязычный интерфейс того же продукта. Часть маршрутов есть
**только на `/es`** (`SPANISH_ONLY_ROUTES`): гиды `/gramatica/*`,
игровые лендинги, 23 страницы `/vocabulary/[categoria]` — это тексты,
объясняющие русский через сравнение с испанским.

**Стек.** Next.js 16.4 (App Router, `--webpack`), React 19.2, TypeScript,
Tailwind. Prisma 7 + **Turso (libsql)** в проде, локально — `dev.db`
(SQLite) в корне. Хостинг **Vercel** (тариф Pro, регион функций `pdx1`),
автодеплой на мерж в `main`. Платежи: на сайте **Stripe**, в приложении —
Google Play через **RevenueCat**. Ошибки — **Sentry**, кэш — **Upstash
Redis**, аудиофайлы — **Vercel Blob**, почта — **Resend**, service worker
— **Serwist**. Node `24.x` (`.nvmrc` 24.22.1), CI — 22.23.4 (7.280).


Числа тестов в прозе устаревают быстрее всего — перемерять, не цитировать.

**Первое в новой сессии — синхронизировать `main`.** Владелец мержит PR
на GitHub, локальный `main` почти всегда отстаёт:

```
git fetch origin --prune
git checkout main && git merge --ff-only origin/main
```

**Прежде чем мерить прод — сверить релиз:**
`curl -s https://rusofacilapp.com/es | grep -o 'sentry-release=[a-f0-9]*'`
против `git rev-parse HEAD`. Документные коммиты Vercel не собирает
(Ignored Build Step, раздел 3.4), поэтому живой релиз = последний коммит,
тронувший не только прозу.

**Локальная база одна — `dev.db` в корне** (`prisma/dev.db` удалён
08.09.2026). Может отставать от прода (пример: «5770 карточек» аудита
7.251 — артефакт устаревшей `dev.db`, на проде 5771). Пересев контента:
`npm run db:pull-bank-from-prod`, `npm run db:pull-content-from-prod`
(без `--apply` ничего не пишут); пользовательские таблицы с прода не
тянуть. Схему локально — `npx prisma migrate diff --from-empty --to-schema
prisma/schema.prisma --script`, затем `ALTER TABLE … ADD COLUMN` /
`CREATE TABLE IF NOT EXISTS`; `prisma db push` не использовать.

**Локальный вход без пароля.** Cookie сессии — HMAC-SHA256 по
`SESSION_SECRET` (`src/lib/session-token.ts`), формат
`userId.sessionVersion.подпись`. Аккаунт с подпиской — регистрация
`POST /api/auth/register` с `Content-Type:
application/x-www-form-urlencoded` (на JSON — 500) + `npm run
db:grant-subscription -- <адрес>`; проверка `check:rendered` сама выдаёт
и снимает грант (`--grant-subscription`, только против localhost).
Стоячих грантов в `dev.db` не держать.

**Мерить прод можно всегда и без кредов:** анонимно по HTTP. Боевую
базу — только по правилам раздела 3.2.

### 1.2. ДАТЫ: часы сервера — единственный источник правды

Любая дата, попадающая в данные (`lastmod`, `updatedAt`, сроки), берётся

раздела. Перед записью проверить, что дата не больше текущей.

### 3.1. Общение, процесс, ветки, PR, мерж

* Владелец не программист: объяснять просто, команды давать готовой
  строкой и говорить, что она делает и что нужно от владельца (27.08).
  Работать без промежуточных вопросов, в конце — один отчёт.
* В `main` напрямую не пушить. Работа в ветке от свежего `main`, PR
  открывает агент, **мержит только владелец**; агент ничего не мержит сам
  (27.08; 7.65 «PR открывает владелец» заменено практикой 7.2xx).
* **Порядок мержа:** PR сайта → «Прод после выката» зелёный → PR оболочки →
  PR документов. Документы — отдельным PR, последним (7.216, 7.266).
* **PR оболочки — с базой `main`, не стопкой над PR сайта** (правило из
  долга 382, 7.267/7.268). После мержа проверять, что исходники дошли:
  `git show origin/main:android/app/build.gradle | grep versionCode`.
* Стопочных PR не делать; после мержа сверять голову PR:
  `git fetch origin 'refs/pull/N/head:refs/tmp/prN'` +
  `git merge-base --is-ancestor`, а не «ветка смержена» (урок #93).
* Правки данных и правки кода — в разных PR; PR данных мержится первым
  (7.90, 7.101). Правка Node/actions в `.github/` — отдельным PR (7.210).
* Если правка трогает списки исключений `check:ci-covers-verify`
  (раздел 5) или строку `verify`, эти строки едут в PR сайта (7.216,
  7.229); вебхук и прочее в одной строке `verify` — одним PR (7.266).
* Перед первым пушем — `npm run verify` целиком; прогон сторожей по
  одному его не заменяет (7.217). Новые файлы — сначала `git add`:
  сторожа смотрят только `git ls-files` (7.205, 7.144).
* Руками не деплоить (`vercel --prod` нельзя): автодеплой на мерж (27.08).
  Временные замерные маршруты — превью-деплоем и удалить до коммита (7.117).
* Пока идёт фоновая сборка/прогон, рабочее дерево не трогать (7.127, 7.216).
* Закрывать вдвое больше долгов, чем заводить; новые долги — только с
  измеренной причиной (7.217, 7.220).
* Перед починкой долга сверить его с продом: он может быть уже закрыт.
* Фикс по скриншоту владельца закрыт, пока не пришёл новый скриншот.
* Бизнес-логику, роутинг, Stripe и схему БД не трогать без просьбы
  (27.08). Крупная правка — без остановки на план: она описывается в
  итоговом отчёте (решение владельца 17.10.2026, раздел 3.19 п. 7;
  `CLAUDE.md`).
* Сырые CSV Search Console, скриншоты и снимки POCO с аватаром владельца
  в репозиторий не кладутся (он публичный) — только сводные числа
  (7.247, 7.269).
* Файл не открывать на запись в том же выражении, где он читается (так
  28.08 был обнулён PROGRESS.md): прочитать → собрать → записать один раз.

### 3.2. Боевая база (Turso), запись в прод

* По умолчанию к проду — **только SELECT**, через обёртку
  `scripts/prod-readonly-query.mjs` (в `.gitignore`, перед работой
  самопроверка подсадками «запись отказана N/N», проверка точки входа, в
  конце удаляется) (7.211, 7.240, 7.265).
* **Запись в прод — только с прямого разрешения владельца**, в отдельном
  заходе: снимок строк до записи вне репозитория
  (`~/rusofacil-backups/<заход>-prod-before.json`), сухой прогон, одна
  транзакция, узкий условный UPDATE с пересчётом условия и поимённой
  сверкой id, проверка `rowsAffected`, сверка после (7.142, 7.266).
* Скрипты данных по умолчанию ничего не пишут (`--apply`/`--dry-run`),
  `--force` без снятого dry-run отвергается; порции — кругами по 10
  (`--only=`), повторный запуск идемпотентен (7.78, 7.106, 7.142).
* Сид по боевой БД: `--dry-run`, диф показать владельцу ДО записи, затем
  `--only=` по согласованным слагам (27.08).
* **Правило 264:** записал данные в прод — в том же заходе пересей
  локальную `dev.db` тем же вызовом с тем же `--only` (7.213).
* Манифест/снимок, посчитанный по `dev.db`, к проду не применять;
  сверять отпечаток банка с продом (7.81–7.84). Рассказы между `dev.db` и
  Turso сопоставлять по (`title`, `level`), не по `id` (27.08).
* `WordGamePuzzle` — только UPDATE по id; удаление каскадом стирает
  `WordGameProgress` (7.4, 7.10).
* Чтение боевой базы — бюджет квоты: тяжёлая перепись — по снимку
  (`npm run snapshot:prod`), в прод только с `--against-prod` и печатью
  цены в строках (`check:prod-reads`); `check:frozen` против прода без
  нужды не гонять (7.172, 7.209).
* **Вход под аккаунтом на проде — это запись** (`persistFreezeState`,
  `POST /api/timezone`); заход «только чтение» на проде не логинится (7.217).
* Схема: изменение — только после «ок» владельца; новые колонки —
  только nullable и без `DEFAULT`; на прод их добавляет
  `prisma/ensure-schema-sync.ts` при сборке, руками в боевую базу не
  пишется (27.08, 7.206, 7.268).
* **Правило 5:** после мержа со сменой схемы проверить
  `curl -o /dev/null -w "%{http_code}" https://rusofacilapp.com/sitemap.xml`
  = 200.
* **503 при отказе базы — решение владельца (в) (7.261):** ничего не
  менять; пересмотреть, если отказы повторятся.
* Индекс `FlashcardCard_russian_idx` (перевод слова по тапу) создан на
  проде 17.10.2026 (7.272, разрешение владельца); везёт его
  `CREATE_INDEX_STATEMENTS` в `prisma/ensure-schema-sync.ts`, сторож
  `check:russian-index`. Откат: `DROP INDEX "FlashcardCard_russian_idx"`.
* Индекс `AudioAsset_text_idx` — BINARY, не NOCASE. `FlashcardCard`
  требует явного `orderBy`. Полная дорожка рассказа — `Story.fullAudioUrl`.
* Сырой UPDATE не двигает `updatedAt`.
* Заход, писавший в прод при замере, удаляет за собой только свои строки.

### 3.5. ЕСЛИ САЙТ УПАЛ — ЧТО ДЕЛАТЬ РУКАМИ; прод после выката

На этот раздел ссылается тревога `prod-down` (`scripts/prod-alarm.mjs`).
Полный текст с пояснениями — архив, часть 01, раздел 2.2 (7.205).

**Как вы узнаете.** (1) Issue с меткой `prod-down` в репозитории —
назначен на владельца, в теле: какая страница, код ответа, снимок, номер
деплоя; закрывается сам следующим зелёным прогоном. (2) UptimeRobot
(письмо и push): `/api/health` по слову `RF-OK` раз в 5 мин, `/es` раз в
30 мин. (3) Глазами.

**Откат за минуту, без терминала.** vercel.com → проект
**rusofacilapp** → **Deployments** → предыдущий деплой **Production**
в состоянии **Ready** (ниже сегодняшнего) → **⋯** → **Instant
Rollback** (или **Promote to Production**) → подтвердить. Номер коммита
живого сайта — в `https://rusofacilapp.com/api/health`, поле `commit`.
**Не «чинить поверх»** — сначала откат, потом разбор.

**После отката.** Ничего нового не мержить, пока причина не найдена;
завести долг; смотреть issue `prod-down`, Sentry, квоту чтений Turso;
починка — отдельным PR. Автооткат — только на втором подряд падении того
же деплоя и только при секрете `VERCEL_TOKEN` (сейчас его нет).

**Порядок выката.** По одному PR; не поздно вечером; после мержа 10 минут
наблюдать (главная, урок, рассказ). Проверка живого прода `smoke:prod`
(workflow `prod-smoke.yml`) идёт сама после выката и раз в час: ожидаемый
код, признак содержимого после гидратации, нет границы ошибок.
`/api/health` — 0 строк квоты, закрыт в robots, не в sitemap.

**Три исхода прогона (7.282, #520).** (1) Зелёный — прод цел. (2) Красный
шаг «Вердикт — прод упал» и issue `prod-down` — прод упал; сюда же — прод,
не ответивший вовсе (отказ соединения, DNS: цель «не ответил»), и прибор,
упавший без отчёта. (3) Красный шаг «Итог — ПРОВЕРКА НЕ СОСТОЯЛАСЬ
(инфраструктура), состояние прода неизвестно» — до прода не дошли
(установка браузеров: зеркала Ubuntu, сеть раннера); issue не заводится,
открытый не закрывается; ждать следующий прогон, при повторах подряд —
смотреть журнал шага «Install Playwright browsers». Установка — 3 попытки
по ≤180 с с паузой 60 с, кеш браузеров по версии Playwright и образу.
Контроль всего прогона — ручной запуск с входом `control`
(`broken_target` / `install_failure`); `broken_target` заводит настоящий
issue с пометкой «КОНТРОЛЬ», его закрывает следующий зелёный прогон.

## 4. ПРАВИЛА ЗАМЕРА — ЧИТАТЬ ДО ТОГО, КАК ПОВЕРИТЬ СВОЕМУ ЗАМЕРУ

Нумерация сохранена: на «PROGRESS.md 4.1» и т. п. ссылается код. Полный
текст с историей каждого правила — архив, часть 01.

### 4.1. «0 проблем» без позитивного контроля — не результат

Проверка, которая отдаёт ноль, сначала показывает, что умеет находить
дефект: подсадить дефект в копию входа и убедиться, что найден. Иначе «0»
— это «0 совпадений». **Сравнение двух пустых выборок обязано падать**, а
не показывать «изменений нет»: в сравнение до/после подсаживается по
одному изменению в каждое поле, плюс проверка, что база живая.
Контроль, который ничего не показал, не выдаётся за пройденный. Известная
оговорка к замеру пишется в файл вместе с числом.

### 4.2. Атрибуты в HTML — только регистронезависимо

Next отдаёт `hrefLang`; флаг `i` и на имя тега; значение — в любых
кавычках или без; разбирать общей функцией.

### 4.3. Длины — на раскодированных сущностях

`&#x27;` — один символ, а не шесть.

### 4.4. Регулярка из данных — только через `escapeRegExp`

Всё из БД, словаря, URL или от человека экранируется (`src/lib/regex.ts`,
дефис как `\x2d`); сборка в try/catch с деградацией; тест проверяет флаг
`u`. Просмотра назад не использовать (`check:no-lookbehind`, Safari <
16.4). Регулярка для `.test()` — без флага `g`.

### 4.5. Фильтр, применённый до замера, — тоже проверка, и он тоже врёт

Контроль фильтра — из спорных случаев; прогнать список через старую и
новую версию фильтра и назвать разницу поимённо; пустой контроль падает.

### 4.6. PROGRESS.md — часть кодовой базы под тестом

`src/lib/progress-doc.test.ts` разбирает этот файл и архив (смешение
алфавитов, повторные заголовки, вопросы холодного старта), а
`check:progress-size` — размер и целость архива. Запись в PROGRESS.md —
правка кода: делается ДО финального `npm test`; порядок — правки → lint →
typecheck → build → test. Сторож не ослабляется.

### 4.7. Прочие правила замера

* Анонимный обход проверяет документы, а не сайт; 200 + «Something went
  wrong» = отказ на клиенте; рендер проверяет `check:rendered`.
* «Локально красный» и «в CI красный» — разные утверждения: CI на пустой
  базе с фикстурой; проверку вида гонять на базе в форме CI.
* После подсаженного дефекта в `src/` пересобрать `.next`; сервер убивать
  по порту; если инструментирование меняет время, «не воспроизвелось»
  ничего не значит.
* Замер с побочным эффектом снимать дважды с каждой стороны; у замера на
  живом устройстве записывать точку отсчёта.
* Тест, держащийся на числе строк прода, — дефект теста.

## 5. СПИСКИ ИСКЛЮЧЕНИЙ CI (МАШИНОЧИТАЕМЫЕ)

Разбирает `npm run check:ci-covers-verify`; каждая метка обязана
встречаться в этом файле ровно один раз. Правило: каждая команда
`verify` гоняется в `ci.yml` или стоит в первом списке с причиной; шаг
`ci.yml`, которого нет в `verify`, — во втором; `check:*`, который не
гоняется нигде, — в третьем. Исключение на команду, которая уже в строю
или которой нет вовсе, — тоже падение.

**Первый список — команды `verify`, которых нет в CI:**

<!-- ci-verify-exceptions:start -->
- `check:story-topics` — в базе CI ноль строк `Story`, и проверка о восьми чипах каталога на пустом каталоге вакуумна: она честно краснеет строкой «в базе нет ни одного рассказа». В CI вместо неё стоит её позитивный контроль `check:story-topics:plant` — он идёт по заведомо здоровой выборке в памяти и базы не спрашивает, то есть само правило под CI проверено целиком. Снимается вместе с фикстурой рассказов или шагом с боевым ключом.
<!-- ci-verify-exceptions:end -->

**Второй список — шаги `ci.yml`, которых намеренно нет в `npm run verify`:**

<!-- verify-ci-exceptions:start -->
- `test:e2e` — Playwright: 291 тест в 28 файлах, три движка, в CI это отдельное задание со своим кэшем браузеров и ~14 минутами прогона. `verify` — гейт ноутбука перед PR, и 14 минут в нём означали бы, что его перестанут запускать.
