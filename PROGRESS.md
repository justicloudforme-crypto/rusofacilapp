**Обновление 27.08.2026 (глубокая ночь) — PR #34 (`feat/seo-glossary-pages`)
падал на Vercel, разобрались и починили, владелец мержит сам:**

**Причина падения — НЕ отсутствие таблицы на проде.** Лог: `Error
[PrismaClientKnownRequestError] ... SQLITE_ERROR: no such table:
main.GlossaryTerm`, в команде `npx tsx prisma/ensure-schema-sync.ts &&
next build --webpack`. Перепроверено дважды (включая прямо сейчас, живым
`curl` на `https://rusofacilapp.com/api/glossary`): **на реальном
проде таблица и все 91 термин есть, отдают 200.** Реальная причина:

1. `generateStaticParams()` в `glossary/[slug]/page.tsx` выполняется
   **на этапе сборки**, а не по запросу.
2. `TURSO_DATABASE_URL`/`TURSO_AUTH_TOKEN` в Vercel заведены **только
   для окружения Production** (проверено `vercel env ls` — для
   сравнения, `BLOB_READ_WRITE_TOKEN` и другие явно помечены
   «Production, Preview», у Turso-переменных только «Production»).
   Любой билд PR — это Preview, у него ни на сборке, ни в рантайме
   этих переменных нет.
3. Без них `src/lib/db.ts` падает по цепочке `TURSO_DATABASE_URL ??
   DATABASE_URL ?? "file:./dev.db"` на несуществующий на билд-
   контейнере Vercel локальный файл — отсюда «no such table» для
   любой таблицы вообще, не только `GlossaryTerm`.
4. `ensure-schema-sync.ts` тут ни при чём — он лишь ADD COLUMN к уже
   существующим таблицам и корректно молча выходит без
   `TURSO_DATABASE_URL` (это его штатное поведение, не баг; трогать
   его не стали, по решению владельца).
5. `force-dynamic` (чем чинили тот же симптом у `sitemap.ts` ранее)
   тут не подходит — `generateStaticParams` сам ЕСТЬ build-time
   механизм, откладывать в рантайм через `dynamic` некуда.

**Починено:** `generateStaticParams` обёрнут в try/catch — при ошибке
(ожидаемо на Preview) логирует понятное сообщение и возвращает `[]`;
уже стоящие `dynamicParams=true`+`revalidate=3600` сами дорендерят
каждую страницу по первому реальному запросу там, где Turso реально
доступен (т.е. на Production). **Проверено против настоящей причины
падения, не только tsc/lint**: `env -u TURSO_DATABASE_URL -u
TURSO_AUTH_TOKEN npm run build` **самим по себе недостаточно** —
локальный `.env` держит `DATABASE_URL="file:./dev.db"`, который
реально существует, так что подмена не долетает до пустого файла, как
на настоящем Vercel. Пришлось ещё и `DATABASE_URL` подменить на
заведомо несуществующий путь — только тогда воспроизвелась та же
самая ошибка «no such table: main.GlossaryTerm» внутри try, лог
сработал, сборка вышла с кодом 0.

**Важное ограничение, НЕ закрыто этим фиксом**: чинили только падение
СБОРКИ. Рантайм Preview **так же** не имеет доступа к Turso (тот же
скоуп переменных) — страница термина по-прежнему не откроется на
Preview-URL этого PR, теперь просто упадёт при запросе, а не на
сборке. Владельцу предложен выбор: (а) завести отдельный **read-only**
Turso-токен под Preview, или (б) мержить без Preview-проверки и
проверять сразу на Production — тем же способом, каким проверяли
рассказы/уроки/медиа весь этот заход. **Решение не принято, ничего в
Vercel/Turso не менялось.**

**Правило на будущее (записать и соблюдать):** перед тем как
предлагать PR с НОВЫМ build-time кодом, который обращается к БД
(`generateStaticParams`, что угодно вне `dynamic="force-dynamic"`),
обязательно прогонять локально:
```
env -u TURSO_DATABASE_URL -u TURSO_AUTH_TOKEN DATABASE_URL="file:/tmp/nonexistent.db" npm run build
```
Просто `env -u TURSO_DATABASE_URL -u TURSO_AUTH_TOKEN` **недостаточно** —
нужно ещё и `DATABASE_URL` подменить на несуществующий путь, иначе
локальный `.env` подставит настоящий `dev.db` и проверка ничего не
поймает (это и произошло с этим PR — проверка для `sitemap.ts` была
сделана правильно раньше в этой же сессии, для `generateStaticParams`
глоссария — забыли повторить).

**Источник данных глоссария — воспроизводимый, не только dev.db.**
`prisma/seed-glossary.ts` — committed в репозиторий, **92 записи**,
upsert по slug (`npm run db:seed-glossary`, есть `--force`), защищает
вручную отредактированные через /admin термины от перезаписи. На
проде сейчас **91** запись — небольшой дрейф (видимо, один термин
объединили/переименовали через админку после сидирования), не
критично, можно свести отдельным разовым проходом при желании.

## Правила, установленные владельцем в этой сессии — НЕ ЗАБЫВАТЬ

Эти правила пришли как прямая реакция на реальные инциденты этой сессии
(см. разделы ниже) — не общие пожелания, а жёсткие ограничения на
дальнейшую работу:

1. **Деплой только из закоммиченного состояния.** Никаких `vercel --prod`
   из локальной папки с несохранёнными правками — именно так на прод
   один раз уехали незакоммиченные файлы (см. «Прод-аут» ниже). Перед
   любым деплоем: `git status` должен быть чист, деплоить то, что уже
   в `main`. Если получится — настроить автодеплой Vercel от GitHub
   (владелец предлагал как альтернативу), тогда этот пункт закрывается
   архитектурно, а не дисциплиной.
2. **Любые изменения схемы БД — только после явного «ок» владельца.**
   Даже если механизм (`ensure-schema-sync.ts`) сам по себе безопасен
   (только добавляет колонки), сам факт добавления колонки в прод —
   решение, которое принимает владелец, не агент.
3. **Озвучка — один раз.** Сгенерировал → сохранил в облако (Vercel
   Blob) → переиспользуешь. Никогда не перегенерировать уже
   озвученный контент (см. «Озвучка» ниже, это уже было золотым
   правилом проекта, но в контексте Бага №1 стоит повторить явно).
4. **Голос рассказчика — один и тот же мужской голос во ВСЕХ рассказах,
   без исключений.** Персонажи внутри рассказа могут (и должны) звучать
   разными голосами — это часть замысла. Но голос самого рассказчика
   не должен меняться по ходу одного рассказа и не должен отличаться
   от рассказа к рассказу. Найден реальный баг с этим в «Теремке» —
   см. «Баг с голосами» ниже, это сейчас блокирует Шаг 2.
5. **Владелец — не программист.** Объяснять простыми словами, без
   жаргона. Любую команду для терминала — готовой строкой, без
   пояснений внутри самой команды, отдельно сказать, что она делает и
   нужно ли что-то ещё от владельца (логин, токен и т.п.).
6. **В `main` напрямую пушить нельзя — только ветка + Pull Request.**
   Проверено дважды подряд (PR #15, PR #16) — прямой `git push origin
   main` из агента не проходит, доезжает только через отдельную ветку
   и PR, который смерживает владелец сам. **Не пытаться `git push
   origin main` напрямую снова** — сразу создавать ветку (например
   `docs/...`/`fix/...` + дата, тот же стиль имён, что уже есть в
   репозитории), коммитить туда, и давать владельцу готовую команду
   вида `git push origin <ветка>` + просить его открыть/смёрджить PR
   (или дать ссылку, если получится её сформировать). Каждый раз
   ПОСЛЕ коммита обязательно проверять `git branch --show-current` —
   в этой песочнице после коммита рабочая копия хотя бы дважды сама
   оказывалась переключена на новую ветку вместо `main`, вероятно
   из-за той же самой защиты `main` на уровне окружения (не git-хук
   в самом репозитории — `.git/hooks/` пустой, проверено). Перед
   любым дальнейшим коммитом на `main`: `git fetch origin`, затем
   `git checkout main && git merge --ff-only origin/main`, чтобы не
   закоммитить поверх устаревшего локального `main`.
7. **Любой перенос данных из локальной `dev.db` в прод-Turso — ТОЛЬКО
   через сопоставление по (`title`, `level`) для `Story`, никогда по
   `id`.** id разошлись у ~315 из 325 рассказов между `dev.db` и
   Turso (не только у `AudioAsset`, как думали раньше — у `Story`
   тоже). Прямой перенос по id уже один раз реально записал фикс не в
   ту строку (см. «Шаг 2c» ниже) — точечная правка «сработала»
   локально и молча ничего не поменяла на проде, пока это не
   вскрылось случайно через unrelated constraint-ошибку при батч-
   переносе. Перед ЛЮБОЙ записью в Turso, где участвует story-контент:
   сначала найти актуальный Turso `Story.id` через `(title, level)`,
   потом уже работать с `AudioAsset` через этот id, никогда через
   локальный.
8. **Новый/перегенерированный аудиофайл — только по новому адресу с
   хэшем содержимого, никогда `allowOverwrite` по старому URL.**
   Vercel Blob кэширует публичные файлы 30 дней — перезапись по тому
   же адресу не гарантирует, что все точки кэша увидят новую версию
   быстро (реальный инцидент с «Теремком», см. ниже). Встроено по
   умолчанию в `concat-story-audio.ts`/`fill-missing-story-audio.ts`
   для любого реального прогона.
9. **Turso-ключ — по запросу, в моменте, без отдельного обсуждения.**
   Когда для задачи нужен прямой доступ к прод-БД — просто попросить
   ключ у владельца. Ключ одноразовый, владелец ротирует его сразу
   после работы. Использовать ТОЛЬКО inline в отдельных командах,
   никогда не сохранять в `.env` или любой файл.

## Озвучка (золотое правило — ЗАФИКСИРОВАНО в CLAUDE.md, коммит `741ae51`)

**Модель/голос**: `gpt-4o-mini-tts` (OpenAI), голос **`onyx`** — только
мужской, единственный по всему проекту (кроме чтения алфавита в уроках,
там отдельная альтернация — не трогать эту логику без явного запроса).

**Хранилище — двухэтапный pipeline, не «сразу в облако»:**
1. Генерация (`prisma/generate-*-audio.ts`) пишет `.mp3` локально в
   `public/audio/{flashcards,stories,lessons,glossary,idioms,exams}/` +
   строку в `AudioAsset` с временным относительным `audioUrl`.
   Каждый клип проходит аудит: обратная транскрипция Whisper, сверка по
   словам (порог 82%, до 5 попыток).
2. Миграция (`npm run migrate:audio-to-blob`, `prisma/migrate-audio-to-blob.ts`)
   грузит файлы в **Vercel Blob** (отдельный публичный стор,
   `AUDIO_BLOB_STORE_ID`/`AUDIO_BLOB_READ_WRITE_TOKEN` — НЕ тот же токен,
   что приватный стор голосовых ответов студентов) и переписывает
   `AudioAsset.audioUrl` на постоянный `https://<store>.public.blob.vercel-storage.com/...`.

## Sentry: SW-регистрация + сорсмапы (ПОЛНОСТЬЮ ЗАКРЫТО)

Прод-ошибка `TypeError: Cannot read properties of undefined (reading
'waiting') at u.register` (issue `7693484267`, event `8de70b2c`) —
разобрана по реальному JSON события, не по догадке.

**Причина №1 (в библиотеке, не в нашем коде):** `@serwist/window`'s
`register()` (`node_modules/@serwist/window/dist/index.mjs:177`)
дереференсит `this._registration.waiting` без проверки. `_registration`
становится `undefined`, если `navigator.serviceWorker.register(...)`
резолвится в `undefined` вместо объекта регистрации/reject — так себя
ведёт заглушка **Playwright** (`serviceWorkers: 'block'` по умолчанию,
`playwright-core/lib/coreBundle.js:51296`:
`register = async () => { console.warn(...) }` без `return`, то есть
резолвится в `undefined`). Наш `playwright.config.ts` целится в
`localhost`, значит по проду ходил внешний Playwright-driven бот, не наш
e2e и не живой пользователь — отпечаток (Chrome 119, San Jose, UTC)
согласуется.

**Причина №2 (наш баг):** в breadcrumbs события — ДВА подряд предупреждения
про Playwright-блокировку, то есть `register()` вызывался дважды. У
`@serwist/window` есть защита от повторной регистрации, но она
**dev-only** и вырезается из прод-сборки. Единственная точка вызова —
`SerwistRegister.tsx`; второй вызов, судя по breadcrumb «навигация /es →
/es» прямо перед падением, шёл от повторного маунта этого компонента.

**Исправлено, 2 коммита:**
- `4d426e9` — модуль-level флаг в `SerwistRegister.tsx`: `.register()`
  вызывается максимум один раз за загрузку страницы, даже при ремаунте.
- `fe82b7c` — `sentry.client.config.ts`: `beforeSend` дропает событие,
  только если ОДНОВРЕМЕННО (a) в breadcrumbs есть warning про Playwright

## Шаг 4 — SEO-аудит (план + находки, ПРАВОК КОДА НЕТ — ждут «ок»
владельца по каждой теме отдельно)

Аудит проведён 27.08.2026 против живого прод-сайта (Lighthouse +
ручная проверка кода). Ничего не менялось — только чтение. Порядок
правок ниже **уже утверждён владельцем**, каждая тема — отдельная
ветка + PR, начинать только после явного «ок» на конкретную тему (не
на весь список разом).

### Утверждённый порядок правок

1. **robots.txt + sitemap.xml, и уникальные title/description** —
   делаем вместе, два самых сильных пункта.
2. **canonical + hreflang**.
3. **JSON-LD**: `Course`/`LearningResource` на уроках, `Article` на
   рассказах, `BreadcrumbList` везде, `FAQPage` на `/pricing` (список
   вопрос-ответ там уже есть, просто не размечен).
4. **TBT 3040ms на странице рассказа** — отдельная задача по
   производительности, не SEO, но не в конец очереди: бьёт по живым
   пользователям на телефоне прямо сейчас.

### Находки (все 7, с конкретикой — что открывать/трогать при правке)

**1. robots.txt и sitemap.xml — отсутствуют полностью.** Самая
крупная находка. `curl https://rusofacilapp.com/robots.txt` и
`/sitemap.xml` не отдают файлы — попадают под общий редирект локали
(`proxy.ts`'s `getPreferredLocale` перехватывает любой путь без
`/ru`/`/es` и шлёт на `/{locale}{pathname}`) и превращаются в мусор.
В коде нет ни `src/app/robots.ts`, ни `src/app/sitemap.ts` (в Next
15/16 App Router это обычные файлы-роуты вне `[lang]`, аналогично
`src/app/manifest.ts`, который уже существует и работает как
образец). Без sitemap Google обнаруживает 325 рассказов + все уроки
только через ссылки со страниц — медленно и ненадёжно.

**2. Canonical — нет нигде.** Единственный файл с метаданными на весь
сайт — `src/app/[lang]/layout.tsx:73-89` (`generateMetadata`),
`alternates.canonical` не задан вообще, ни здесь, ни на дочерних
роутах. Риск дублей в индексе: `/pricing?next=...`,
`/profile?tab=...`, `/stories?level=...&topic=...`.

**3. hreflang между /ru и /es — нет вообще.** Тот же
`layout.tsx:73-89`: `alternates.languages` не задан. Google не знает,
что `/ru/stories/xxx` и `/es/stories/xxx` — одна и та же страница на
двух языках.

**4. title/description — одинаковые на КАЖДОЙ странице сайта.**
`src/app/[lang]/layout.tsx:73-89` — единственный `generateMetadata` во
всём приложении, берёт `dict.meta.title`/`dict.meta.description`
(фиксированная пара на язык, не на страницу). Ни один дочерний route
(урок, рассказ, статья медиатеки, уровень) не переопределяет
`generateMetadata` — у всех 325 рассказов и всех уроков в поиске
будет один и тот же заголовок «RusoFácilapp — учите русский язык...».
Самое сильное простое улучшение из всех 7 находок.

**5. Структурированные данные (JSON-LD) — не найдено вообще.** Ни
`application/ld+json`, ни `schema.org` не встречаются нигде в коде.
Кандидаты: `Course`/`LearningResource` для уроков, `Article` для
рассказов, `BreadcrumbList` везде, `FAQPage` на `/pricing` (готовый
список вопрос-ответ уже есть в разметке, просто без schema).

**6. Core Web Vitals на мобильном — Lighthouse (симуляция throttling),
27.08.2026:**

| Страница | Performance | LCP | CLS | TBT |
|---|---|---|---|---|
| Главная (`/ru`) | 67 | 3.7s | 0 (отлично) | 600ms (плохо) |
| Урок (`/ru/courses/a1/1`) | 85 | 3.0s | 0 | 380ms |
| Рассказ (Теремок) | **58** | 3.6s | 0.027 | **3040ms (очень плохо)** |

Худшая страница — рассказ: TBT 3 секунды означает, что главный поток

  магазин); код проверен только typecheck/логикой, не живым рендером.

## Правила работы (полный текст — в CLAUDE.md)

Mobile-first (375px → 768px → 1280px). Все стили — только через
дизайн-токены. **primary** — единственный кликабельный акцент,
**premium** — только некликабельные маркеры (enforced check:tokens).
Минимальный тач-таргет 44×44px. Capacitor подтверждён — safe-area/
`100dvh`/без `position:fixed` на инпутах/обработка «Назад». Не трогать
бизнес-логику/роутинг/Stripe без явной просьбы. План и остановка перед
крупными структурными изменениями. Каждый шаг — отдельный коммит,
откатываемый одной командой. После каждого шага —
check:tokens/lint/typecheck/тесты/build, затем **живая проверка
владельцем на телефоне**, прежде чем идти дальше.

Полные обоснования — в **AUDIT.md** (база багов/несоответствий) и
**CLAUDE.md** (правила проекта, мобильные особенности Capacitor, золотое
правило озвучки).
